# Kotlin 임베딩 모델 및 재색인 설계

## 상태

2026년 9월 17일 대화에서 승인했다.

## 목적

Kotlin 검색 기능이 DB에 저장된 임베딩 모델 설정을 사용하게 한다.

모델 변경과 관리자가 요청한 전체 재색인을 안전하게 처리한다. 기존
커넥터 수집 흐름을 재사용한다. Python의 문서 복사 방식은 이식하지 않는다.

## 선택한 방식

Python의 기존 `REINDEX` 방식을 따른다.

1. 현재 색인은 검색과 일반 증분 색인을 계속 처리한다.
2. 대상 색인에서 커넥터별 첫 색인을 실행한다.
3. 첫 색인이 끝나면 범위가 고정된 최종 증분 색인을 한 번 실행한다.
4. 커넥터와 대상 색인 설정별 결과를 기록한다.
5. 필요한 커넥터가 모두 성공하면 자동으로 전환한다.
6. 전환 후에는 이전 색인의 작업을 더 예약하지 않는다.

다음 방식은 사용하지 않는다.

- 저장된 문서를 색인 사이에서 복사하지 않는다. 이 방식은 별도 커서,
  삭제 정합성 처리, 재시도 상태가 필요하다.
- 수동 활성화, 배포, 중단, 삭제 기능을 만들지 않는다. 기존 커넥터 수명
  주기에 맞춰 자동으로 전환한다.

## 범위

### 포함

- Granite와 Harrier 로컬 임베딩 모델
- DB 기반 현재, 준비 중, 과거 색인 설정
- 기존 커넥터 로더와 처리기를 사용한 전체 재색인
- 호환되는 과거 색인의 증분 동기화
- 모든 커넥터 성공 후 자동 전환
- 커넥터별 재시도와 실패 전체 재시도
- 준비 중인 색인 작업 취소
- 임베딩 공급자 기능과 사용하지 않는 문서 복사 스키마 제거

### 제외

- OpenAI 호환 방식을 포함한 원격 임베딩 공급자
- 저장된 문서를 색인 사이에서 복사하는 Python 문서 복사 흐름(`port flow`)
- 수동 색인 배포 및 검색 경로 전환
- 전환 후 이전 색인에 대한 지속적인 갱신
- 동기화하지 않은 과거 색인으로 즉시 전환하는 기능

## 로컬 모델 목록

백엔드는 지원 모델을 정의한 정적 JSON 파일 하나를 관리한다. 프런트엔드는
백엔드 API에서 모델 목록을 받는다. 프런트엔드에 같은 목록을 중복해서 두지
않는다.

초기 모델은 다음과 같다.

| 모델 | 차원 | 정규화 | 최대 문맥 길이 |
| --- | ---: | --- | ---: |
| `ibm-granite/granite-embedding-311m-multilingual-r2` | 768 | true | 512 |
| `microsoft/harrier-oss-v1-0.6b` | 1024 | true | 512 |

JSON에는 모델별 질의 접두사와 문서 접두사도 넣을 수 있다. 초기 두 모델은
현재 로컬 실행기의 동작을 그대로 사용한다.

로컬 모델 추가는 명시적인 코드 변경으로 처리한다. 모델 목록, 모델 서버,
테스트, 모델 파일 문서를 함께 수정해야 한다.

모델 서버는 모델 준비 상태를 계속 제공한다. Harrier 파일이 있을 때만
Harrier를 선택할 수 있다. 반환된 벡터는 등록된 차원과 같아야 한다. 모든
값은 유한한 숫자여야 한다.

## DB 상태

`search_settings`에는 모델 선택과 색인 수명 주기에 필요한 값만 저장한다.

- `id`
- `model_name`
- `index_name`
- `status`
- `singleton_marker`
- `reindex_started_at`
- `cutover_at`
- `cancel_requested_at`
- 생성 시각과 수정 시각

차원, 정규화, 문맥 길이, 접두사는 정적 모델 목록에서 가져온다. 같은 값을
DB에 중복해서 저장하지 않는다.

`PRESENT` 설정은 하나만 존재한다. `FUTURE` 설정도 최대 하나만 존재한다.
모델마다 물리 색인 이름을 두 개만 사용하므로 설정도 최대 두 개만 유지한다.
사용하지 않는 설정 행은 새로 만들지 않고 재사용한다.

`PRESENT` 설정이 없으면 애플리케이션 시작 시 Granite 설정을 만든다. 물리
색인 이름에는 설정된 OpenSearch 기본 색인 이름을 사용한다. 임베딩 모델
환경변수는 초기 설정과 이후 실행에 사용하지 않는다.

검색과 일반 수집은 항상 `PRESENT` 설정을 조회한다.
`ModelServerClient.defaultConfig()`는 사용하지 않는다.

## 스키마 정리

새로운 순방향 마이그레이션을 추가한다. 기존 V17 마이그레이션은 수정하지
않는다.

다음 공급자 관련 객체를 제거한다.

- `embedding_providers` 테이블
- `search_settings.provider_type`
- 공급자 열거형, 엔티티, 저장소, API, 서비스
- 공급자 자격 증명 암호화 코드
- 모델 서버의 공급자 요청 필드와 외부 HTTP 호출 경로

정적 모델 목록에서 제공하는 다음 컬럼도 제거한다.

- `search_settings.model_dim`
- `search_settings.normalize`
- `search_settings.query_prefix`
- `search_settings.passage_prefix`

사용하지 않는 문서 복사 상태도 제거한다.

- `reindex_port_attempts` 테이블
- `connector_credential_pairs.full_recollect_requested`

`reindex_started_at`과 `cancel_requested_at`은 유지한다. 최종 증분 범위를
저장하기 위해 `cutover_at`을 추가한다.

## 커넥터 상태 분리

수집 시도, 작업, 체크포인트, 색인 문서 상태, 관련 조회에는 대상
`search_settings_id`가 있어야 한다.

작업을 구분하는 기준은 다음과 같다.

`커넥터 자격 증명 쌍 + 색인 설정`

이 구조를 사용하면 현재 색인의 일반 수집과 대상 색인의 전체 재색인을 함께
실행할 수 있다. 과거 색인이 마지막으로 성공한 위치도 유지할 수 있다.

작업 중복 방지와 임대도 같은 기준을 사용한다. 같은 커넥터와 같은 대상
색인을 두 작업이 동시에 갱신할 수 없다. 현재 색인 작업과 대상 색인 작업은
서로 독립적으로 실행할 수 있다.

기존 수집 코드는 다음 기능을 계속 담당한다.

- 수집 시각 범위
- 커넥터 페이지 체크포인트
- 문서 처리
- 삭제 문서 정리
- 작업 임대
- 오류 저장

수집 시도는 대상 설정에서 모델과 물리 색인 이름을 가져온다. 검색은
`PRESENT` 설정에서 두 값을 가져온다. 인자가 없는 임베딩 메서드나 고정된
OpenSearch 색인 이름이 이 경로를 우회하면 안 된다.

대상 수집 시도 행이 전환에 필요한 커넥터 목록이 된다. `FUTURE` 작업 중에
새 커넥터를 추가하면 현재 색인과 대상 색인 작업을 모두 만든다. 새 커넥터도
전환 조건에 포함한다. 커넥터를 삭제하면 관련 작업을 취소하고 전환 조건에서
제외한다.

## 색인 이름

모델마다 기본 색인과 보조 색인 이름을 하나씩 사용한다. 같은 모델로 전체
재색인을 실행하면 현재 사용하지 않는 이름에 기록한다. 같은 이름의 `PAST`
설정이 있으면 초기화한 뒤 재사용한다.

이 방식은 현재 검색 중인 색인에 재색인 결과가 섞이는 것을 막는다. 전체
재색인을 반복해도 물리 색인이 계속 늘어나지 않는다.

증분 전환은 호환되는 과거 색인을 재사용한다. 모델 이름과 정적 모델 사양이
모두 같아야 호환되는 것으로 판단한다.

## 전체 재색인

`Full Reindex`는 항상 표시한다. 원본 시스템 요청과 임베딩 부하가 클 수
있으므로 빨간색 위험 버튼으로 표시한다.

다음 순서로 처리한다.

1. 다른 `FUTURE` 작업이 있으면 요청을 거부한다.
2. 선택한 모델에서 현재 사용하지 않는 물리 색인을 고른다.
3. 해당 설정을 만들거나 초기화하고 `FUTURE`로 바꾼다.
4. 필요한 커넥터마다 `fromBeginning=true` 수집 시도를 만든다.
5. 기존 커넥터 처리 흐름으로 작업한다.
6. 첫 전체 수집에 성공한 커넥터는 같은 전체 수집을 다시 실행하지 않는다.
7. 모든 커넥터가 성공하면 최종 전환 단계를 시작한다.

일시 중지된 커넥터도 기존 색인 문서가 있으면 재색인 대상에 포함한다.
재색인은 커넥터의 저장된 일시 중지 상태를 바꾸지 않는다. 재색인에서 한 번
실행한 뒤에도 일시 중지 상태를 유지한다.

문서 또는 개체 오류가 있는 커넥터는 전환 성공 조건을 충족하지 않는다.
관리자가 해당 커넥터를 다시 실행해 성공시켜야 한다.

## 증분 동기화 및 전환

호환되는 `PAST` 색인이 있을 때만 `Sync & Switch`를 표시한다.

다음 순서로 처리한다.

1. 호환되는 `PAST` 설정을 `FUTURE`로 바꾼다.
2. 현재 색인이 계속 갱신되는 동안 첫 동기화 상한 시각을 기록한다.
3. 각 커넥터가 대상 색인에서 마지막으로 성공한 위치부터 시작한다.
4. 시각 기반 수집에는 기존 중복 구간을 그대로 적용한다.
5. 중단된 커넥터는 저장된 페이지 체크포인트부터 이어서 처리한다.
6. 첫 동기화가 성공하면 최종 전환 단계를 시작한다.

전역 중단 시각 하나만으로 커넥터 진행 상태를 표현하지 않는다. 커넥터마다
수집 위치와 페이지 위치가 다르다. 색인 설정별 커넥터 상태를 기준으로 삼는다.

## 최종 전환 기준 시각

전환 기준은 DB 시각이다. 문서 ID, 원본 ID, 자동 증가 행 번호를 사용하지
않는다.

최종 전환 단계는 다음 순서로 처리한다.

1. 새로운 `PRESENT` 수집 작업 예약을 중지한다.
2. 대기 중인 `PRESENT` 작업을 중지한다.
3. 실행 중인 작업이 끝나거나 임대를 반환할 때까지 기다린다.
4. DB 현재 시각을 한 번 읽고 `cutover_at`에 저장한다.
5. 모든 대상 커넥터에 같은 `poll_range_end = cutover_at`을 지정한다.
6. 각 커넥터는 대상 색인의 마지막 성공 `poll_range_end`부터 시작한다.
7. 원본 시스템 시각 오차를 보완하는 기존 중복 구간을 적용한다.
8. 기존 삭제 문서 정리 작업을 실행한다.
9. 고정 범위 수집과 삭제 정리가 모두 성공하면 전환한다.

4단계 이후에는 대상 범위가 늘어나지 않는다. 원본 문서가 빠르게 생성돼도
전환 작업이 끝없이 이어지지 않는다.

`cutover_at` 이후 변경분은 원본 시스템에 남아 있다. 전환 후 새 현재 색인의
첫 증분 작업이 `cutover_at`부터 기존 중복 구간을 적용해 수집한다. 전환 중에도
검색은 계속 가능하다. 수집 최신성만 잠시 멈춘다.

저장된 기준 시각을 사용하므로 재시도와 서버 재시작도 같은 범위를 처리한다.

최종 대상 작업이 실패하면 현재 색인 작업 예약을 다시 시작한다. 전환은
중단된 상태로 유지한다. 재시도는 저장된 범위를 끝낸다. 이후 현재 작업을
다시 멈추고 새 기준 시각을 저장한 뒤 마지막 고정 범위를 한 번 더 처리한다.
원본 문서 생성 속도 때문에 이 과정이 반복되지는 않는다. 작업 실패가 있을
때만 다시 실행한다.

전환 전에는 대상 색인의 문서 집합 소속과 DB 기반 색인 메타데이터도 현재
상태로 맞춘다. 원본 문서 삭제는 커넥터의 삭제 문서 정리가 담당한다.

## 자동 전환

필요한 커넥터마다 최종 고정 범위 수집과 삭제 정리가 성공해야 한다. 실패,
취소, 미완료 작업이 하나라도 있으면 전환하지 않는다.

한 DB 트랜잭션에서 다음 상태를 함께 변경한다.

- 현재 `PRESENT`를 `PAST`로 변경
- 대상 `FUTURE`를 `PRESENT`로 변경
- `singleton_marker` 제약 유지
- 일반 작업 예약 대상을 새 `PRESENT`로 변경

커밋 후에는 이전 색인 작업을 취소한다. 이미 실행 중인 작업은 대상이 더는
현재 색인이 아님을 확인하고 종료할 수 있다. 이전 색인 작업은 새로 예약하지
않는다.

이전 물리 색인과 커넥터별 마지막 위치는 유지한다. 나중에 `Sync & Switch`로
되돌릴 수 있다.

## 취소와 재시도

`Cancel`은 `FUTURE` 작업에만 적용한다.

취소 요청은 `cancel_requested_at`을 기록한다. 대상 작업은 안전한 묶음 처리
경계에서 멈춘다. 대상 임대가 더는 쓰기를 할 수 없을 때까지 기다린다. 이후
미완성 물리 색인과 `FUTURE` 설정을 삭제한다. 현재 색인은 변경하지 않는다.
최종 전환 때문에 현재 작업을 멈춘 상태라면 다시 예약한다.

`Retry`는 선택한 실패 커넥터만 다시 실행한다. `Retry All`은 실패한 커넥터를
모두 다시 실행한다. 성공한 커넥터의 작업은 반복하지 않는다.

재시도는 기존 수집 범위와 페이지 체크포인트를 유지한다. 실패한 범위를
건너뛰거나 성공한 커넥터까지 처음부터 다시 실행하면 안 된다.

## 관리자 화면

Kotlin 관리자 사이드바에서 기존 색인 설정 경로를 활성화한다.

화면에는 Granite와 Harrier만 표시한다. 현재 모델에는 `Current`를 표시한다.
버튼과 진행 상태에는 다음 영어 문구를 사용한다.

- `Sync & Switch`
- `Full Reindex`
- `Cancel`
- `Retry`
- `Retry All`
- `Syncing…`
- `Reindexing…`

작업이 없을 때 `Full Reindex`를 항상 표시한다. 호환되는 과거 색인이 있을
때만 `Sync & Switch`를 표시한다.

작업 중에는 전체, 완료, 실행 중, 실패한 커넥터 수를 표시한다. 상세 내용은
기존 커넥터 상태 화면으로 연결한다. 별도 색인 현황판이나 수동 검색 경로
전환 기능은 만들지 않는다.

## 실패 및 동시 실행 규칙

- `FUTURE` 작업은 하나만 허용한다.
- 첫 대상 작업 중에는 현재 색인의 읽기와 쓰기를 유지한다.
- 범위가 고정된 최종 전환 단계에서만 현재 색인 쓰기를 잠시 멈춘다.
- 일부 커넥터만 성공한 상태에서는 전환하지 않는다.
- `COMPLETED_WITH_ERRORS`를 전환 성공으로 처리하지 않는다.
- 만료된 작업은 기존 임대 방식으로 이어서 실행한다.
- 외부 쓰기는 커넥터와 대상 색인 기준으로 차단한다.
- 준비되지 않은 로컬 모델의 작업 버튼은 비활성화한다.
- 정적 모델 목록과 차원이 다른 벡터는 거부한다.
- 일시 중지된 커넥터의 저장 상태는 바꾸지 않는다.

## API 구성

현재 및 준비 중인 색인 설정 조회 API는 유지한다. 공급자 중심 계약은 로컬
모델과 재색인 작업 API로 바꾼다.

백엔드는 다음 기능을 제공한다.

- 로컬 모델 목록과 준비 상태 조회
- 선택한 모델로 전체 재색인 요청
- 호환되는 과거 색인의 증분 동기화 및 전환 요청
- 대상 작업 진행 상황 조회
- 활성 대상 작업 취소
- 실패한 커넥터 하나 재시도
- 실패한 커넥터 전체 재시도

기존 프런트엔드 서비스 경로가 새 기능과 맞으면 재사용한다. 사용하지 않는
공급자 계약을 위해 별도 API 버전이나 호환 계층을 만들지 않는다.

## 검증

이 기능은 DB, 작업 예약기, OpenSearch를 함께 변경한다. 통합 테스트를
우선한다.

백엔드에서 다음 내용을 검증한다.

- 마이그레이션이 공급자와 문서 복사 객체를 제거한다.
- 현재 설정이 없으면 시작 시 Granite를 만든다.
- 검색과 수집이 DB에서 선택한 모델과 색인을 사용한다.
- 전체 재색인 중 현재 색인을 유지하고 모두 성공하면 전환한다.
- 최종 전환이 DB 시각 하나를 저장하고 모든 커넥터에 같은 상한을 준다.
- 기준 시각 이후 변경분을 새 현재 색인이 수집한다.
- 같은 모델의 전체 재색인은 사용하지 않는 물리 색인을 사용한다.
- 실패한 커넥터가 전환을 막는다.
- 재시도가 성공한 커넥터를 반복하지 않는다.
- 일시 중지된 커넥터가 저장 상태를 바꾸지 않고 재색인에 참여한다.
- 증분 동기화가 대상 색인의 커넥터별 마지막 위치부터 시작한다.
- 증분 동기화가 전환 전에 삭제 문서를 정리한다.
- 최종 전환이 문서 집합 메타데이터를 맞춘다.
- 최종 증분 실패 시 현재 작업을 재개하고 새 기준 시각을 요구한다.
- 취소가 쓰기 작업 종료를 기다리고 미완성 대상만 삭제한다.
- 벡터 차원이 다르면 잘못된 쓰기 전에 실패한다.

프런트엔드에서 다음 내용을 검증한다.

- 로컬 모델만 표시한다.
- `Full Reindex`를 항상 표시하고 위험 버튼 스타일을 사용한다.
- 호환되는 과거 색인이 있을 때만 `Sync & Switch`를 표시한다.
- 진행, 취소, 재시도 문구가 승인된 영어 문구와 같다.

Granite와 Harrier의 기존 모델 서버 테스트는 유지한다. 삭제한 원격 공급자
구현의 테스트도 함께 제거한다.

## 문서 변경

Kotlin 실행 문서와 모델 서버 문서에 다음 내용을 반영한다.

- Granite는 DB 초기 기본 모델이다.
- Granite와 Harrier만 임베딩 모델로 지원한다.
- 모델 선택은 `search_settings`와 정적 모델 목록을 사용한다.
- 임베딩 모델 환경변수는 더는 실행 설정이 아니다.
- 원격 임베딩 공급자와 문서 복사 흐름(`port flow`)은 지원하지 않는다.
