# ADR: 현행 질문에 최신 근거 순위를 함께 적용한다

- 상태: 제안
- 작성일: 2026-09-17
- 적용 대상: Kotlin 검색 MCP와 답변 지침

## 결정

현행 상태를 묻는 질문에는 관련도 순위와 최신성 순위를 함께 사용한다.
같은 주제를 다루는 근거가 충돌하면 더 최근에 갱신된 문서를 우선한다.
단, 최신 문서가 질문과 관련 있다는 조건을 먼저 충족해야 한다.

두 순위는 기존 `weighted_reciprocal_rank_fusion` 도구로 결합한다.
초기 가중치는 관련도 `1.0`, 최신성 `0.3`으로 제안한다.
이 값은 운영 최적값이 아니다. 평가 자료로 조정해야 한다.

과거 시점이나 변경 이력을 묻는 질문에는 최신성 우선 규칙을 적용하지 않는다.
이 경우 질문이 지정한 시점과 문서의 유효 시점을 우선한다.

오래된 문서를 삭제하거나 검색에서 일괄 제외하지 않는다.
답변 모델은 충돌 사실과 각 근거의 갱신 시각을 함께 표시한다.

## 배경

현재 검색은 키워드와 벡터 관련도를 중심으로 결과를 정렬한다.
`doc_updated_at`은 응답 메타데이터에 포함된다.
그러나 이 값은 `time_cutoff` 하한 필터 외에는 순위 계산에 쓰이지 않는다.

관련 코드는 다음 위치에 있다.

- `_kotlin/backend/src/main/kotlin/com/onyx/kotlin/opensearch/OpenSearchIndexer.kt`
- `_kotlin/backend/src/main/kotlin/com/onyx/kotlin/opensearch/OpenSearchChunkDocument.kt`
- `_kotlin/backend/src/main/kotlin/com/onyx/kotlin/mcp/McpSearchTool.kt`

실제 사례에서는 서로 다른 Confluence 페이지가 같은 업무 개념을 설명했다.
2026년 5월의 중간 문서는 이벤트 Enum 다섯 종류를 기록했다.
사업 범위가 줄어든 뒤 2026년 8월 문서는 세 종류를 기록했다.
기존 하이브리드 검색은 5월 문서를 더 높게 배치했다.
그 결과 현행 질문에 과거 다섯 종류가 답으로 나왔다.

이 문제는 날짜만으로 모든 문서를 정렬해서 해결할 수 없다.
최신이지만 무관한 문서가 관련 근거를 밀어낼 수 있기 때문이다.

## 질문 의도

답변 모델은 질문 의도에 따라 검색 방식을 선택한다.
별도 영구 라벨은 필요하지 않다.

### 현행 상태

다음 표현을 포함하거나 같은 뜻인 질문이다.

- 현재, 지금, 현행, 최신
- 현재 지원하는 값이나 정책
- 지금 저장소 기준 구현
- 별도 시점이 없는 현재형 질문

현행 상태 질문은 관련도 검색과 최신성 검색을 함께 수행한다.

### 과거 시점과 변경 이력

다음 질문은 최신성 우선 대상이 아니다.

- 특정 날짜 당시의 상태
- 변경 전후 비교
- 의사결정 과정과 폐기된 대안
- 프로젝트 중간 산출물의 내용

답변 모델은 지정 시점에 맞는 근거를 찾는다.
현행 상태와 다르면 차이를 함께 설명한다.

### 의도가 불명확한 질문

기본값은 현행 상태다.
충돌이 답에 큰 영향을 주면 현재 상태와 과거 기록을 구분해 표시한다.

## 검색 절차

1. 기존 하이브리드 검색으로 후보군을 넓게 가져온다.
2. 관련도가 낮은 후보는 제거한다.
3. 남은 후보를 기존 관련도 순서로 둔다.
4. 같은 후보를 `doc_updated_at` 내림차순으로 다시 정렬한다.
5. 두 목록을 WRRF로 결합한다.
6. 상위 근거의 문맥을 조회한다.
7. 값이 충돌하면 양쪽 근거를 답변 모델에 전달한다.

후보군은 기존 검색 최대치 50 안에서 시작한다.
별도 전역 최신 문서 검색은 만들지 않는다.
이 방식은 무관한 최신 문서가 결과를 차지하는 위험을 줄인다.

`doc_updated_at`이 없는 문서는 최신성 목록의 뒤에 둔다.
날짜가 없다는 이유만으로 관련도 목록에서 제거하지 않는다.
날짜가 같은 문서는 관련도 순서를 유지한다.

## 답변 규칙

답변 모델은 근거 종류를 영구 저장하거나 수동 라벨링하지 않는다.
검색 결과의 출처와 질문 의도를 실행 시점에 해석한다.

현행 상태 질문에서는 다음 순서를 사용한다.

1. 코드 근거가 있으면 현재 메인 브랜치 구현을 우선한다.
2. 문서 근거만 있으면 더 최근의 관련 문서를 우선한다.
3. 정책 문서와 구현이 다르면 둘을 합치지 않는다.
4. 현재 구현과 문서상 의도를 각각 표시한다.
5. 충돌과 확인 시각을 숨기지 않는다.

코드 근거 연동은 별도 CodeGraph 준비 문서의 후속 범위다.
이 ADR의 첫 적용은 문서 검색 순위와 답변 지침이다.

## 청킹 기준

첫 단계에서는 의미 기반 청킹을 도입하지 않는다.
현재 모델 서버는 Chonkie `SentenceChunker`로 문장을 토큰 한도에 맞춰 나눈다.
이 동작은 큰 블록을 자르는 마지막 단계로 재사용할 수 있다.

수집기는 먼저 원천 구조를 보존해야 한다.

### Confluence

- 제목과 상위 제목 경로를 청크 문맥에 넣는다.
- 제목 구역, 표, 코드 블록, 목록을 가능한 한 분리하지 않는다.
- 댓글은 본문과 다른 종류의 블록으로 유지한다.
- 토큰 한도를 넘는 블록만 문장 단위로 나눈다.

### Jira

- 설명, 현재 필드, 댓글을 서로 다른 블록으로 유지한다.
- 댓글의 작성 시각과 작성자를 보존한다.
- 상태와 해결 결과 같은 현재 필드는 설명에 섞지 않는다.
- 토큰 한도를 넘는 블록만 문장 단위로 나눈다.

이 방식은 별도 임베딩 모델이나 의미 경계 판정 모델이 필요 없다.
먼저 구조 손실이 실제 검색 오류를 줄이는지 평가한다.

## 평가

다음 사례를 고정 평가 자료로 만든다.

- 같은 주제의 5월 문서와 8월 문서가 충돌한다.
- 과거 시점을 묻고 오래된 문서가 정답이다.
- 더 최신이지만 질문과 무관한 문서가 있다.
- 일부 문서에 `doc_updated_at`이 없다.
- 두 문서의 갱신 시각이 같다.
- 오래된 문서만 존재한다.
- 최신 관련 문서가 기존 검색 상위권 밖에 있다.

다음 지표를 기록한다.

- 최신 관련 근거 재현율
- 정답 근거의 최종 순위
- 충돌 표시 성공률
- 잘못된 최신성 우선 비율
- 기존 관련도 평가의 변화

가중치는 이 평가를 통과한 뒤 확정한다.

## 결과와 제한

이 결정은 기존 메타데이터와 WRRF를 재사용한다.
새 분류 모델과 문서 삭제 정책은 추가하지 않는다.

`doc_updated_at` 자체가 잘못되면 최신성 순위도 잘못될 수 있다.
원천별 날짜 정확성, 삭제 지연, 같은 논리 문서의 복사본 문제는
`_kotlin/WATCHLIST.md`의 `WL-20260911-001`에서 계속 추적한다.
